4. ETAPA 1 - LEXER
--------------------------------------------------------------------------------
4.1 Palavras reservadas, operadores, delimitadores (seções 1 a 3 do .g4)
    Mantidos como a dupla escreveu. Regras de funcionamento do ANTLR que explicam por que
    funciona: (a) o ANTLR escolhe o MAIOR casamento, então "maer_an" ganha de "maer" e
    "calad_gwath" ganha de "calad"; (b) em empate de tamanho vale a regra declarada primeiro,
    por isso as reservadas vêm antes de ID. Cada palavra composta é um token indivisível.
    "u", "hi", "aur_din", "vi", "garo" NÃO são reservadas: viram ID.

4.2 Literais numéricos (seção 5.2 do enunciado)
    INT_LITERAL    0 | [1-9][0-9]* | 0b[01]+ | 0x[0-9a-fA-F]+      (prefixos só minúsculos)
    FLOAT_LITERAL  D '.' [0-9]+ [expoente]?  |  D expoente        D = 0 | [1-9][0-9]*
    O sinal negativo é um operador separado (-2.5 = MINUS FLOAT_LITERAL).

    Regra do "candidato completo": 0b102 não pode virar 0b10 + 2, 007 não pode virar 0 0 7,
    2contador não pode virar número + identificador. Implementação sem código Java: a regra
    INVALID_NUMBER casa o candidato inteiro (começa por dígito e engole letras, marcas,
    dígitos, "_" e "."). Como o ANTLR usa o maior casamento, INVALID_NUMBER vence sempre que
    o candidato é maior que o numeral válido; quando o numeral é válido há empate e a regra
    válida (declarada antes) vence.
    O sinal + ou - só entra no candidato logo depois de e/E quando tudo antes é [0-9.]
    (1e+, 2.5e-2). Por isso 0xE+1 são 3 tokens (INT_LITERAL PLUS INT_LITERAL), como pede o PDF.

4.3 Strings
    STRING_LITERAL: aspas duplas, sem CR/LF/U+0000, escapes só \n \r \t \" \\.
    INVALID_STRING casa a string defeituosa até o fim da linha. O código Java diz o MOTIVO
    (sem aspas de fechamento, escape inexistente, U+0000) e aponta a posição certa: no
    início da string (sem fechamento) ou na barra/NUL (escape/NUL). Não existe literal com
    aspas simples: ' vira ERROR_CHAR.

4.4 Identificadores
    ID: [\p{L}_] [\p{L}\p{M}\p{Nd}_]*   (letra Unicode ou _; depois letras, MARCAS de acento,
    dígitos Unicode ou _). RESERVED_IDENTIFIER (declarado antes de ID) rejeita nomes que
    começam com dois sublinhados, que o enunciado reserva para a implementação.

4.5 Espaços e comentários
    Ignorados (skip): espaço, tab, CR, LF; // até o fim da linha; /* ... */ sem aninhamento.
    Qualquer outro espaço Unicode (ex.: U+00A0) vira ERROR_CHAR (erro léxico), como pede o PDF.
    UNTERMINATED_COMMENT casa um /* sem fechamento; a expressão só casa texto que NÃO contém
    "*/", então um comentário bem fechado continua sendo BLOCK_COMMENT.
    Aspas dentro de comentários não abrem string, e // ou /* dentro de string são texto
    (testado em tests/1-lexer/validos/05).

4.6 Última regra: ERROR_CHAR : . ;
    Garante que um caractere inválido gere UM token de erro apontando só aquele caractere
    (sem ela, o ANTLR juntaria o caractere ruim com o seguinte na mensagem).

4.7 UTF-8, acentos e NFC (exigido na seção 23.1)
    - O arquivo é lido como UTF-8 ESTRITO: byte inválido é erro de leitura (código de saída 2),
      sem trocar nada por "?".
    - Um BOM no início do arquivo é aceito e descartado (não conta como coluna); U+FEFF em
      qualquer outro lugar é ERROR_CHAR.
    - O texto NÃO é normalizado. Comentários e strings chegam exatamente como estão.
    - Palavra reservada escrita em NFD (u + acento combinante) não casa com o literal do .g4,
      que está em NFC. Mas a regra ID ACEITA marcas combinantes, então a palavra vira um ID.
      A classe SindarinLexerNfc, a cada ID, normaliza o texto para NFC e consulta a tabela de
      reservadas; se achar, TROCA O TIPO do token (o texto e a posição continuam os originais).
      A tabela é montada a partir dos literais do próprio lexer gerado, então não fica
      dessincronizada. Teste: tests/1-lexer/validos/02 (NFD) dá os mesmos tokens que o 01 (NFC).
    - Dois identificadores iguais após NFC são o mesmo nome: SindarinLexerNfc.nfc(texto) está
      disponível para a tabela de símbolos (Etapa 4) comparar nomes.

4.8 Linha e coluna
    O ANTLR só reconhece LF como quebra de linha. O enunciado manda contar CRLF, CR e LF como
    UMA quebra e contar colunas em pontos de código. Por isso Posicoes.java calcula linha e
    coluna a partir de Token.getStartIndex() (índice em pontos de código) e o projeto não usa
    Token.getLine(). Testes 21 e 22 de tests/1-lexer/invalidos cobrem CR e CRLF.

5. ETAPA 2 - PARSER
--------------------------------------------------------------------------------
5.1 Estrutura do programa (regra inicial: programa)
      programa : blocoRecursos declaracaoGlobal* declaracaoFuncao* blocoSetup blocoLoop EOF
    EOF é obrigatório: tokens depois do fechamento de cor são erro. Todo bloco é
    "cabeçalho mi { ... }"; o mi aparece em gwaith, minui, cor, curu, maer_an, egor_mi,
    curu_egor, curu_min, cor_maer, cor_pad e cor_nedia. No laço cor_caro o mi abre o corpo e
    NÃO há mi antes da condição final: cor_caro mi { } cor_maer cond;

5.2 Regras principais
    declaracaoRecurso   tipoRecurso ID = ceber(N) | ceber_nen(N) [: expressao] ;
    declaracaoConstante sador tipo ID = expressao ;
    declaracaoVariavelGlobal  tipo ID [= expressao] ;       (inicializador opcional)
    declaracaoVariavelLocal   tipo ID = expressao ;         (inicializador obrigatório)
    declaracaoFuncao    curu tipo ID ( parametros? ) mi bloco   (procedimento = tipo pen)
    tipo                inteiros com largura, nen, maer_peth, calad_gwath, peth, cen_min,
                        aur / aur<hí>, pen e vetor [tipo; N]  (sem vetor aninhado)
    comando             atribuição, ação (caro ...), minui_peth, condicional, seleção,
                        cor_maer, cor_pad, cor_nedia, cor_caro, methed, cor_minui, dandol
    acao                caro (pedo | pedo_meth | pedo_min | aur_dîn | an ID (caro_calad|caro_nen) | chamada) ;
    condicional         maer_an expr [an nome] mi bloco [egor_mi mi bloco]   (forma de presença)
    selecao             curu_egor expr mi { curu_min expr mi bloco ... [egor_mi mi bloco] }
    lacoPara            cor_pad ( init? ; expr? ; atualizacao? ) mi bloco

5.3 Precedência (da maior para a menor) - uma regra por nível, o nível mais baixo chama o mais alto
      1  primário, chamada, acesso a vetor, parênteses     (primario)
      2  û e - unários                (direita)             (expressaoUnaria)
      3  *  /  %                      (esquerda)            (expressaoMultiplicativa)
      4  +  -                         (esquerda)            (expressaoAditiva)
      5  == != < <= > >=  mesmo nível, NÃO encadeiam        (expressaoRelacional)
      6  a   (e lógico)               (esquerda)            (expressaoE)
      7  egor (ou lógico)             (esquerda)            (expressaoOu)
    O que impede "a < b < c" é o "?" (zero ou uma vez) em
        expressaoRelacional : expressaoAditiva (operadorRelacional expressaoAditiva)?
    Demonstração (nedia x = 10 + 5 * 2;): na árvore, 5 * 2 fica DENTRO de um mesmo
    expressaoMultiplicativa, que é filho do "+":
        expressaoAditiva
          expressaoMultiplicativa -> 10
          PLUS '+'
          expressaoMultiplicativa -> 5  STAR '*'  2
    Operações sobre bits (a_min<8>(x, y) etc.), conversões (nedia(x), nen(x)), aur(n, d),
    cen_calad recurso e cen_nen recurso são "primarios".

5.4 Regras do enunciado que o PARSER já faz cumprir
    - atribuição é comando: "x = y = 1;" e "maer_an (x = 1) mi {}" são erros sintáticos;
    - "caro" só existe em ações; "mostrar(5);" sem caro, "caro valor = 1;" e "caro (mostrar(3));" são erros;
    - escrita na placa só na ordem  caro an recurso caro_calad|caro_nen expressao;
    - methed e cor_minui não aceitam parênteses; não existe comando vazio ";";
    - cor_pad exige os dois ";" mesmo com partes vazias; chamadas no cabeçalho são "caro nome(args)"
      sem ";" final;
    - curu_egor exige pelo menos um caso; egor_mi é opcional, único e último;
    - declaração local sem inicializador é erro; global pode não ter.

5.5 Decisões de interpretação (o PDF é ambíguo ou deixa em aberto - podem ser ajustadas)
    a) Ordem no topo do arquivo: seguimos a forma normativa da seção 22 ("declaraçõesGlobais
       funções"): TODAS as globais antes de TODAS as funções.
    b) "pen" e as larguras (nedia<7>) são aceitos pelo PARSER em qualquer posição de tipo;
       restringir onde cada tipo pode aparecer é semântica (o enunciado diz que as formas de
       tipo são reconhecidas na sintaxe e o uso é restringido na semântica).
    c) minui_peth taxa; é aceito como comando em qualquer bloco. Exigir que seja o 1º item de
       minui e ocorrer uma única vez é verificação semântica (Etapa 4).
    d) "[]" (lista vazia) é aceito no parser e rejeitado na semântica, como diz o PDF.
    e) Pino/canal, largura, tamanho de vetor, taxa serial e os dois argumentos de aur(n, d)
       são INT_LITERAL (numerais), nunca expressões.
    f) Parâmetro pode ser tipo de dado OU tipo de recurso (parâmetro de capacidade: nen_caro saida).

5.6 Fica para a semântica (Etapa 4), de propósito
    Nomes declarados/duplicados, tipos e larguras permitidas, constância, pinos do Mega,
    retorno por caminho, methed/cor_minui fora de laço, ordem inicial de minui, número de
    elementos de vetor, tipo da condição, vetor sem tamanho, etc. "Passar no parser não torna o
    programa válido" (seção 22 do enunciado).

5.7 Mensagens de erro sintático
    Português, com a posição do PRIMEIRO token que a gramática não aceitou, o que era esperado
    e dicas para os enganos mais comuns (falta de "mi", falta de ";"). Para um ";" esquecido,
    a posição é a do token seguinte (padrão do ANTLR). O ANTLR continua analisando depois do
    primeiro erro e pode listar mais mensagens; no relatório de testes conta só a primeira
    (seção 26.4 do enunciado: não contar mensagens em cascata como defeitos independentes).
    Regra do pipeline: havendo erro léxico, o parser NÃO roda (evita cascata).

5.8 Verificação de ambiguidades
    Os 8 programas válidos foram analisados com DiagnosticErrorListener e modo
    LL_EXACT_AMBIG_DETECTION: nenhuma ambiguidade reportada. Duas regras foram fatoradas
    (acao -> "caro" + corpoAcao; atribuicao com indiceVetor?) para que o parser decida com 1
    token e a mensagem "esperado: ..." fique correta.
